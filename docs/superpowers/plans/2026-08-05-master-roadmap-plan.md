# 授業プラットフォーム化ロードマップ 全体マスター計画

作成日: 2026-08-05

## この文書の役割

これは個別フェーズの実装計画（例: `docs/superpowers/plans/2026-08-05-phase0-safety-and-baseline-plan.md`）とは別の、**上位の進行管理ドキュメント**である。実装手順は書かない。フェーズ間の順序・依存・判断のタイミング・外部依存・授業での検証・中断再開のための状態記録のみを扱う。

正本は次の2つ。内容が食い違った場合は正本を優先し、本ドキュメントを更新する。

- `docs/superpowers/specs/2026-08-05-lesson-platform-roadmap-design.md`（設計の正本）
- `docs/superpowers/plans/2026-08-05-phase0-safety-and-baseline-plan.md`（Phase 0 の実装計画。0a/0bの分割はここが出典）

具体的な日付・工数の見積もりはここには書かない。根拠がないためである。書くのは「Aの前にBが要る」という順序関係のみ。

## 1. フェーズ一覧と依存関係

設計ドキュメントの「フェーズ構成」表（`lesson-platform-roadmap-design.md:543`）を出発点に、Phase 0 の 0a/0b 分割（phase0計画の「実施単位の分割」）と Phase 1 の6段階（同design.md:585-664）を反映して整理する。

### フェーズ全体の依存図

```
Phase 0a（安全化）─→ 1.1 → 1.2 → 1.3 →┬→ 1.4 → 1.5 ─┬─→ Phase 2 ─→ Phase 3
                                       │        1.6 ─┤
Phase 0b（基準値計測）─────────────────┘             ├─→ Phase 4
                                                     └─→ Phase 5 ─┬─→ Phase 6
                                                                  └─→ Phase 7
```

**0b が止めるのは 1.4 であり、Phase 1 全体ではない**（下記「0b と Phase 1 の関係」を参照）。

### Phase 0 内部（0a / 0b）

- **0a（安全化。phase0計画 Task 1〜8）**: コード・ルール・移行の変更のみで完結する。0b の完了を待たずに着手・出荷できる（phase0計画に明記: 「0a を 0b の完了に依存させてはならない」）。
- **0b（基準値計測。phase0計画 Task 9〜13）**: staging Blazeプロジェクトと有人の負荷試験を要する。ただし phase0計画 Task 12 は「修正前」「修正後」の2回の計測を求めており、**「修正後」計測は 0a の完了に依存する**。「修正前」計測は 0a 着手前でも実行できる。

  → 0a と 0b は並行して準備を進められるが、0b の「修正後」計測の実行だけは 0a の完了を前提とする。この非対称性は phase0計画にのみ明記されており、設計ドキュメントのフェーズ表（Phase 0 を単一行として扱う）には現れていない。

#### 0b と Phase 1 の関係（レビューによる確定）

設計ドキュメントの「フェーズ構成」表は Phase 0 を単一行として扱い、Phase 1 が Phase 0 全体に依存すると読める（`design.md:545-546`）。**この扱いは採用しない。** 0b は有人の負荷試験を含むため、Phase 1 全体の前提にすると純粋なコード作業まで長期間止まる。

**0b が前提となるのは 1.4 以降である。**

| 段階 | 0b の完了が必要か | 理由 |
| --- | --- | --- |
| 1.1 組織の器 | 不要 | `orgId` / `createdByUid` の付与のみ。価格エンジンに触れない |
| 1.2 スキーマとバージョン管理 | 不要 | 型とデータ構造の定義のみ。稼働中の挙動を変えない |
| 1.3 Functions基盤 | 不要 | `functions/` の新設と `pricingCore` の切り出し。ティック挙動は変わらない |
| **1.4 ラウンド進行と一括約定** | **必要** | ここで初めてティック挙動が変わり、計測済みの基準値が「変更前」として意味を持つ |
| 1.5 / 1.6 | 必要（1.4 経由） | |

0b は 1.1〜1.3 と並行して進める。0b の staging Blaze プロジェクト用意と、1.3 の本番 Blaze 移行はいずれも Blaze 契約を要するため、まとめて着手すると効率がよい。

### Phase 1 内部（1.1〜1.6）

設計ドキュメントは「依存関係のある6段階で構成する」（`design.md:587`）と明記しており、番号順の直列進行が基本になる。

```
1.1 組織の器
  ↓（全ドキュメントへ orgId / createdByUid を付与。以降すべての新規ドキュメントの前提）
1.2 LessonTemplate v2 スキーマとバージョン管理
  ↓（rounds / events / assessment 等のスキーマが 1.4〜1.6 の実装対象を定義する）
1.3 Cloud Functions基盤と価格の秘匿
  ↓（settleRound 等はCloud Function前提。pricingCore共有もここで固定）
1.4 ラウンド進行と一括約定
  ↓（settleRound が存在して初めて、銘柄別影響・需給連動・注文への紐づけができる）
1.5 銘柄別ニュースと需給連動  ─┐
1.6 予想・判断理由の記録と振り返り ─┘（いずれも1.4に依存。1.5と1.6の間には設計ドキュメント上の直接依存は明記されていない）
```

#### 1.5 と 1.6 の関係（レビューによる確定）

両者は 1.4 に依存するが、互いには依存しない。**並行して実装してよい。** ただし一点だけ順序がある。

1.6 の「ニュースと株価を重ねた時系列グラフ」は、1.5 の銘柄別ニュース影響が入って初めて意味を持つ。ニュースが全銘柄一律のままでは、重ねて表示しても「どの銘柄にどう効いたか」が読み取れない。

したがって次の扱いとする。

- 1.5 と 1.6 の実装本体は並行してよい
- 1.6 のうち**ニュース重ね合わせの部分だけ**は 1.5 の完了後に結合する
- 1.6 の他の要素（個人予想の入力、判断理由の紐づけ、チーム内の予想比較、個人単位の削除・エクスポート）は 1.5 と無関係に完成させられる

### Phase 2 以降

- Phase 2（授業運用）、Phase 4（家庭科モード）、Phase 5（組織・ライセンス・決済）は、いずれも Phase 1 全体（1.1〜1.6すべて）にのみ依存し、**互いには依存しない**。3つは並行して着手できる。
- Phase 3（AI Lesson Studio ベータ）は Phase 2 に依存する（`LessonIntent` を Guided Lesson Builder と共有するため）。Phase 5（課金基盤）には依存しない — 設計ドキュメントが「AIを課金基盤より前に置く」「ライセンス基盤に依存しない」と明記している（`design.md:554`, `:711`）。
- Phase 6（マーケットプレイス）と Phase 7（エンタープライズ管理者機能）はいずれも Phase 5 に依存し、**互いには依存しない**。並行着手が可能。

### 並行できる組み合わせ／直列にすべき組み合わせ

| 並行可能 | 直列が必要 |
| --- | --- |
| 0a の実装作業と 0b のインフラ準備（staging Blaze等） | 0a の完了 → 0b の「修正後」計測 |
| **0b と 1.1〜1.3**（0b は価格エンジンに触れない段階を止めない） | **0b → 1.4** |
| 0b の staging Blaze 用意と 1.3 の本番 Blaze 移行（まとめて着手すると効率的） | 1.1 → 1.2 → 1.3 |
| 1.5 と 1.6（本体は並行可。1.6 のニュース重ね合わせのみ 1.5 の後） | 1.4 → 1.5・1.6 |
| Phase 2 / Phase 4 / Phase 5 | Phase 1（全段階）→ Phase 2・4・5 それぞれ |
| Phase 3 と Phase 5（相互に非依存） | Phase 2 → Phase 3 |
| Phase 6 と Phase 7 | Phase 5 → Phase 6・7 |

## 2. 各フェーズの完了条件

設計ドキュメントで明示的に「完了条件」として書かれているのは **Phase 0 のみ**である（`design.md:573-581`）。他のフェーズは目標や実装内容の記述はあるが、チェックリスト形式の完了条件は書かれていない。捏造せず、そのまま「未定義」として扱う。

### Phase 0a（安全化）— 完了条件（design.mdの完了条件のうち、コード・ルール・文書化に関する項目。phase0計画のTask分類に基づき分類）

- 生徒アカウントで `endPrice`、`seed`、`phases` のいずれも取得できないこと
- Rules Emulator のテストで先読み経路を検証済みであること（生徒・教師それぞれの読み取り可否）
- クラシックモードの既知の制約（ホスト依存、毎秒更新）を文書化済みであること

### Phase 0b（基準値計測）— 完了条件（同上、インフラ・計測に関する項目）

- staging の Blaze プロジェクトで50分・80人相当の負荷試験を実施済みであること（phase0計画は計測時間短縮の検討を推奨事項として付記している）
- Cloud Monitoring でプロトコルを含む送信バイト数を記録済みであること
- Firebase の使用状況画面の帯域量と突き合わせ済みであること
- 書き込み回数とデータサイズを記録済みであること

### Phase 1（1.1〜1.6 全体）— 未定義

チェックリスト形式の完了条件はない。「検証の方針」節に目標として次の1文があるのみ（`design.md:1007`）:

> Phase 1完了時点で、社会科のラウンド制授業が実施可能な状態になることを目標とする。

これは目標であって完了条件のチェックリストではない。1.1〜1.6それぞれの「実装内容」は本文（`design.md:589-664`）に列挙されているが、「何をもって完了とするか」の基準（例: テスト網羅率、性能条件、教師による受け入れ確認の要否）は書かれていない。**Phase 1 の着手前、遅くとも1.4完了前後までに定義する必要がある。**

### Phase 2〜7 — 未定義

Phase 2（授業運用）、Phase 3（AI Lesson Studio ベータ）、Phase 4（家庭科モード）、Phase 5（組織・ライセンス・決済）、Phase 6（マーケットプレイス）、Phase 7（エンタープライズ管理者機能）はいずれも、実装すべき機能の列挙はあるが完了条件は書かれていない。各フェーズの個別実装計画を書く時点で定義することになる（本マスター計画は実装計画そのものではないため、ここでは定義しない）。

## 3. 判断が必要なタイミングの一覧

設計ドキュメント「リスクと未決事項」表（`design.md:942-967`）をフェーズの進行順に並べ替えたもの。「決定済み」の項目はどのフェーズも待たずに使える確定事項として先頭にまとめ、残りは決定時期のフェーズ番号順に並べる。

### すでに決定済み（どのフェーズの着手も妨げない）

これらは Phase 1 の実装（主に1.3〜1.5）の前提として既に固まっている。

| 項目 | 現時点の方針 |
| --- | --- |
| ラウンドモードの約定価格 | 売買中の公開価格で約定し、需給は次ラウンドへ反映 |
| 価格変化の合成 | 変化率を加算し ±20% で丸める |
| チーム注文の競合 | `revision` による楽観的並行制御 |
| 権限ミラーの同期 | Firestore を正本とし、単一 Callable に集約。不整合時は拒否側へ倒す |
| クラシックモードのサーバー化 | 行わない。ノード分離のみ |
| クラシックモードの約定価格 | ホストが最後に公開した価格を鮮度確認して使う。サーバーは再計算しない |
| テンプレートの公開範囲 | 実行時に公開／エンジン／教師の3状態へコンパイルする |
| 組織削除時のトークン失効 | 使わない。`status` の変更で足りる。グローバル失効の用途に限定する |
| 需給計算の入力 | 含めない。検証後の約定予定数量のみを使う |

### 未決事項（決定時期のフェーズより前に着手できない作業がある）

| 項目 | 決める内容 | 決定時期 | この判断をしないと着手できない作業 |
| --- | --- | --- | --- |
| v1からv2への移行 | 稼働中の市場がv1由来の場合の扱い | Phase 1.2 | 1.2のv1→v2変換関数・バックフィル戦略の実装 |
| 価格の丸め仕様 | 丸め方法、最低価格、上限、適用順序 | Phase 1.3 | 1.3のpricingCore共有関数（クライアント/サーバー共通）の実装 |
| 価格計算式の二重実装 | クライアントとサーバーで式がずれるリスクへの対処 | Phase 1.3 | 1.3のpricingCoreモジュール共有・一致検証テストの実装 |
| 表示価格と約定価格の乖離（クラシックモード） | 生徒が見た価格と約定価格がずれる扱い | Phase 1.3 | 1.3のクラシックモード価格提示方法の実装 |
| オフライン時の扱い | 売買フェーズ中に切断した生徒の提出の扱い | Phase 1.4 | 1.4の売買フェーズ注文保存・再送処理の実装 |
| 自動進行 | 教師操作かタイマーか | Phase 1.4 | 1.4のラウンド状態遷移の実装 |
| `sensitivity` と `marketDepthWeight` | 需給が価格をどの程度動かすか、既定値 | Phase 1.5 | 1.5の需給連動の実装・既定値設定（試運転で決めるとされているため、Phase 2の試運転モードとも関係） |
| 個人予想とプライバシー | 未成年の個人回答の保存範囲・匿名化・削除方法 | Phase 1.6 | 1.6の個人予想記録・削除機能の実装 |
| AIベータの対象者 | 誰に開放するか | Phase 3 | Phase 3のアクセス制御（利用者を運営者許可アカウントに限定する仕組み）の実装 |
| 共有リンクの失効 | 学校組織向けに失効可能な共有が必要 | Phase 5 | Phase 5の共有リンクv2形式（`revokedAt`/`expiresAt`）の実装 |
| 決済事業者 | 選定 | Phase 5 | Phase 5の決済導入作業 |
| テンプレート所有権 | 学校退職・異動時の扱い | Phase 5 | Phase 5の教材の複製・移動・共有・派生機能の実装 |
| マーケットプレイスの審査体制 | 誰が・どの基準で審査するか（未定。政治的中立性を基準へ含める） | Phase 6 | Phase 6の審査ワークフロー・運営者向け審査画面の実装 |

## 4. 外部依存とリードタイム

自分だけでは完了できない項目。着手のかなり前から動き出す必要がある。

| 項目 | 関連フェーズ | 何のために必要か | いつまでに動き出すべきか |
| --- | --- | --- | --- |
| staging Blaze プロジェクトの用意 | Phase 0b | Task 9〜13（負荷試験、Cloud Monitoringでの計測）の前提 | Phase 0bのTask 9着手前。0aと並行して準備を始められる |
| 有人の負荷試験（人が50分×2回拘束される） | Phase 0b | Task 12（修正前・修正後の計測） | 「修正前」計測は0a着手前から実施可能。「修正後」計測は0a完了後にしか実行できないため、0a完了のタイミングに合わせて人の予定を確保する必要がある |
| Blazeプランへの移行と予算アラート設定（本番プロジェクト） | Phase 1.3 | Cloud Functions基盤の稼働、予算超過時のアプリ側停止機構の前提 | Phase 1.3着手前。なお0bで使うstaging Blazeプロジェクトとは別物（本番プロジェクトの移行） |
| 決済事業者の選定 | Phase 5 | 決済導入作業の前提。学校・自治体単位の年間ライセンスを想定するため、契約形態の検討にも時間を要する | Phase 5着手のかなり前。Phase 2〜4の並行期間中に選定を始めることが望ましい |
| 学校の情報管理規程・契約・プライバシーポリシーへの適合確認 | Phase 1（正式提供前） | 「具体的にどこまでが法令上の必須要件かは…正式提供の前に確認する」（design.md:558）。未成年の学習・行動データを扱うため | Phase 1の正式提供（実運用開始）前。学校側・法務側との調整を要するため早期着手が必要 |
| 実際の授業での検証（学期・時間割に依存） | 各フェーズ完了時（詳細は次節） | 「検証の方針」に基づく、各フェーズ完了後の実授業でのフィードバック取得 | 対象授業の学期・時間割が決まるタイミングに合わせて、フェーズ完了予定より前に学校・教員との調整を始める必要がある |

## 5. 各フェーズ完了後の授業での検証

設計ドキュメントの「検証の方針」は次の1点のみを明言している（`design.md:1003-1007`）。

> 各フェーズの完了時に、実際の授業で使用してフィードバックを得てから次へ進む。全フェーズを実装してから初めて実運用に出す進め方は取らない。Phase 1完了時点で、社会科のラウンド制授業が実施可能な状態になることを目標とする。

これを踏まえ、各フェーズの内容から検証対象として妥当な授業の形を整理する。**Phase 1以外は設計ドキュメントが明示していないため、フェーズの実装内容からの推定であることを明記する。**

| フェーズ完了後 | 検証できる授業の形 | 根拠・備考 |
| --- | --- | --- |
| Phase 0a / 0b | なし（設計ドキュメントに記載なし） | 脆弱性の解消と基準値計測は生徒・教師に見える機能変化を伴わない。既存授業（クラシックモード等）が引き続き問題なく動くことの確認は必要だが、これは「新しい授業形態の検証」ではなく回帰確認にあたる |
| **Phase 1** | **社会科（公民・政治経済）のラウンド制授業** | 設計ドキュメントが明示する目標。ラウンド進行・一括約定・需給連動・銘柄別ニュース・個人予想記録がすべて揃って初めて成立する授業形態 |
| Phase 2 | Phase 1と同じ社会科ラウンド制授業を、Research Desk／コントロールルーム／試運転モード／Guided Lesson Builderを使って運用する | Phase 2は新しい教科領域を追加しない。既存のラウンド制授業の運用品質（教師の進行負担、生徒の画面の分かりやすさ）を検証する位置づけ（design.md:665-708の内容から推定） |
| Phase 3 | Phase 2までと同じ社会科（`LessonIntent.subject`はこの時点で`SOCIAL_STUDIES`/`CUSTOM`のみ。design.md:694）の授業を、AIとの対話で設計して実施する | 限定ユーザーへの提供。「教師がAIとの対話に何を求めるか」を検証する目的（design.md:711）であり、対象教科自体はPhase 1〜2と同じ社会科である |
| Phase 4 | **家庭科（家庭基礎・家庭総合）の授業**（資産形成・生活設計） | 設計ドキュメントが明示（`design.md:752-772`）。株式売買と異なるデータモデルのため独立したサブプロジェクト |
| Phase 5 | 授業単体ではなく、学校組織としての運用パイロット（招待・ロール・決済を含む組織単位の受け入れ確認） | 設計ドキュメントに「授業での検証」という形の記載はない。Phase 5は組織・ライセンス・決済という運用基盤であり、単一授業では検証しきれない。**この検証形態は設計ドキュメントに定義がなく、別途定義が必要** |
| Phase 6 | 授業単体ではなく、複数組織にまたがる教材の公開・検索・複製の運用確認 | 同上。**設計ドキュメントに定義がなく、別途定義が必要** |
| Phase 7 | 授業単体ではなく、学校管理者による組織単位のメンバー・データ統制の運用確認 | 同上。**設計ドキュメントに定義がなく、別途定義が必要** |

## 6. 中断・再開のための状態記録

一人で長期間かけて進めるため、中断して戻ってきたときにここを見れば現在地が分かるようにする。**状態は作業のたびに手動で更新すること。**

### 再開時に確認する順番

1. 上表で「進行中」または直近で「完了」になったフェーズを確認する
2. そのフェーズの実装計画ドキュメント（あれば）の未完了タスクを確認する
3. 本文「3. 判断が必要なタイミングの一覧」で、次に着手するフェーズに紐づく未決事項が決定済みか確認する
4. 「4. 外部依存とリードタイム」で、次に着手するフェーズに必要な外部依存（staging環境、Blaze移行、決済事業者、学校調整など）の準備状況を確認する
5. 直前に完了したフェーズについて、「5. 各フェーズ完了後の授業での検証」に沿った実授業での検証・フィードバック取得が済んでいるか確認する
