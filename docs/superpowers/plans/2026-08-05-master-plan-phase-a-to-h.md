統合仕様書 §25「実装順」は Phase A〜H の中身を箇条書きするだけで、依存関係・完了条件・判断のタイミング・外部依存・状態記録を明示していない。本文書はそれらを補う上位の進行管理ドキュメントであり、各Phaseの実装手順（タスク分解、コード、テストコード）は書かない。各Phaseの実装計画は別文書として今後作成する。

## 1. Phase A〜H の依存関係

### 1.1 依存図

```text
Phase A（安全化と新基盤）
  │  orgId・個人組織・権限ミラー・失効・共通イベントログ・冪等処理・
  │  教材/版/授業実施モデル・個人データ削除/エクスポート
  ▼
Phase B（共通授業基盤）
  │  教師/生徒/教室表示・参加/チーム/待機・フェーズ・入力部品・
  │  自動保存・チェックポイント・復旧・介入・結果・アンケート・分析
  ├──────────────┐
  ▼              ▼
Phase C          Phase D
（社会科完成）    （家庭科完成）
  │              │
  └──────┬───────┘
         ▼
      Phase E（AI・教材作成強化）
         │
         ▼
      Phase F（組織・契約）※A・Bへの直接依存は必須。C・Eへは内容依存（1.2参照）
         │
         ▼
      Phase G（マーケットプレイス）
         │
         ▼
      Phase H（エンタープライズ管理）
```

C と D は互いに依存せず、両方が B にのみ依存する兄弟関係。E はその2つの合流点になる。F 以降は直列。

### 1.3 並行できる組み合わせ／直列にすべき組み合わせ

| 並行可能 | 直列が必要 |
| --- | --- |
| **Phase C と Phase D**（相互に非依存。両方が B にのみ依存） | A → B |
| Cのうち需給・ノイズ・価格ガード等の細部実装と、Dのフェーズ設計の細部実装（互いに参照しない） | B → C、B → D（それぞれ独立に） |
| Fの組織・招待・教師席・課金CRUD の実装と、C・D・Eの実装（Fの本体はA・Bのみに依存するため） | C・D → E（Eの完全な機能にはCとD両方が必要） |
| — | E → F の「利用枠」統合テスト（§27.5を市場軸・AI軸両方で検証する部分のみ）。F本体のCRUDはB完了後すぐ着手できる |
| — | F → G（Gの公開資格判定がFの学校組織設定を参照する） |
| — | (C または D) → G（公開する教材の実体が必要） |
| — | G → H（Hの管理画面がGの承認・公開ワークフローをラップする） |

### 1.4 統合仕様書からは判断できず自分で決めた箇所

- **F の「必須依存」をA・Bのみとし、C・Eへは「内容依存（ソフト依存）」に格下げした点。** §25はFをEの後に置いているが、これはF本体のCRUD（組織・招待・教師席・課金状態の保存）が動くために必須という意味ではなく、利用枠の一部の軸（市場数・AIクレジット）が意味を持つために必要という理解に基づく。統合仕様書はこの区別を明示していない。
- **G が C・D のうち「どちらか一方」で着手可能とした点。** §17は社会科・家庭科を区別せずに一般論として書かれており、両方の完成を要求する記述はない。実務上は先に完成した方の教材から公開を試せるはずという判断。
- **H が A・F・G の3つに依存すると整理した点。** §20は個々の管理メニューがどのPhaseの機能をラップするかを明言していないため、§20.1のメニュー構成（生徒データ＝A、契約・利用枠＝F、教材＝G）から逆算して依存関係を組み立てた。

## 2. 各Phaseの完了条件

### 2.1 §27 受け入れテストの対応表

統合仕様書 §27 は「セキュリティ／市場／授業／家庭科／組織・課金」の5分類。各項目をPhaseへ割り当てる。

#### §27.1 セキュリティ → 主に Phase A、一部 B・C・E

| 受け入れテスト項目 | 割り当てPhase | 根拠 |
| --- | --- | --- |
| 生徒が非公開価格情報を読めない | A（基盤）／C（具体的検証） | §26-1・§26-3の型・パス分離はAの基盤タスク。価格そのものはCで初めて実在する |
| 別組織の教材・結果を読めない | A | orgId所有・権限ミラーそのもの |
| 停止済みメンバーが授業へアクセスできない | A（失効モデル）／B（授業アクセス制御として検証） | §6.6失効はA、実際の授業アクセス制御はB |

#### §27.2 市場 → Phase C（11項目すべて）

同一区間の全注文が同価格／二重送信が1回だけ約定／処理中取消不可／資金不足の買い注文が全不成立／同一区間売却代金が購入に使われない／参考価格と約定価格が履歴に残る／価格ガードを下回らない／倒産時だけ0円になる／停止後注文が受理されない／再開確認時間後に同時受付／リプレイで同じイベント列を再現できる。すべて§12の社会科市場機構に対応し、Phase Cの完了条件そのもの。

#### §27.3 授業 → Phase B（7項目すべて）

教材版固定後、元教材編集が影響しない／教師端末切断後も別教師が引継可能／生徒が別端末で復帰可能／欠席・途中参加が状態を壊さない／途中終了から再開可能／教室表示に禁止情報が出ない／アンケートと結果が紐付く。すべて§25 Phase Bの「教師、生徒、教室表示／参加、チーム、待機／復旧／介入／結果／アンケート」に対応。

#### §27.4 家庭科 → Phase D（6項目すべて）

資産、保険、負債、キャッシュフローが分離／物価・金利が指定項目へ反映／資金不足時に選択肢が出る／同一条件モードで全チームの初期条件が一致／人生段階をまたいで保存・再開／価格・税率等の教材版が固定。すべて§13に対応し、Phase Dの完了条件そのもの。

### 2.3 どのPhaseにも割り当てられない項目

以下は §31 に項目として存在するが、統合仕様書 §25 の Phase A〜H いずれの箇条書きにも文字通りには出現しない。横断的な性質を持つため、単一Phaseへの割り当てを強制せず、ここに明示する。

- **通知**（§23.3）: 内容が「開始・終了・締切・緊急停止」（B相当）、「ニュース・決算」（C相当）、「株価更新」（C相当）にまたがる。B〜Dの各Phaseで機能追加のたびに通知種別を追加していく横断機能として扱う。
- **ヘルプ**（§23.4）: 「注文できない理由」（C）、「次へ進めない理由」（B/D）など全画面共通の仕組み。B着手時に土台を作り、C・D完了まで拡張し続ける。
- **アクセシビリティ**（§23.5）: 全画面・全Phaseに適用される横断要件。単一の完了Phaseを持たない。
- **ステータス・サポート**（§24）: 内容が「AI停止」（E）、「アップロード停止」「市場作成停止」（C）、「緊急組織モード」（H）にまたがる運用機能。バックアップ（§24.1）自体はAの直後から必要だが、ステータスページ・緊急組織モードはH（エンタープライズ管理）の管理画面と一体で作るのが自然。

#### 横断要件の扱い（レビューによる確定）

「機能追加のたびに追記する」という運用にはしない。実際には忘れられる。**画面を追加するすべてのPhase（B・C・D・E・H）の完了条件に、次の固定チェックを組み込む。**

| 項目 | 各Phaseで確認すること | 根拠 |
| --- | --- | --- |
| 通知 | このPhaseで追加した操作・イベントすべてに、重要／通常／参考の区分を割り当てた | §23.3 |
| ヘルプ | このPhaseで「できない理由」を表示すべき箇所を洗い出し、実装した | §23.4 |
| アクセシビリティ | このPhaseで追加した画面に §23.5 の各項目を適用した | §23.5 |
| 表示名 | このPhaseの画面が §23.6 の表示名規則を守っている | §23.6 |

アクセシビリティは性質上、単一Phaseで「完了」しない。後から全画面へ遡って適用するのは現実的でないため、各Phaseの完了条件として扱うのが唯一機能する方法である。

**ステータス・サポート（§24）は割り当て不能ではなく、下位項目ごとに分割する。**

| 下位項目 | Phase | 理由 |
| --- | --- | --- |
| バックアップ（§24.1） | A の直後 | 保護すべきデータが存在した時点から必要 |
| 市場作成停止・アップロード停止（§24.2の一部） | C | 既存の `serviceStatus` を拡張する。停止対象が生まれる時点 |
| AI停止（§24.2の一部） | E | 同上 |
| ステータスページ | C 完了後（授業で実運用を始める時点） | 障害を外部へ通知する必要が生じる時点 |
| 緊急組織モード・運営者アクセス（§24.3） | H | 組織管理画面と一体 |

なお §16.2（複製）・§16.3（共同編集）も §25 の箇条書きには出現しない。判断: 複製はB（教師の日常的な授業管理機能）、共同編集はE（教材作成強化のテーマに沿う。§16.3自身が「初期はリアルタイム共同編集を必須にしない」としており後回しでよい機能であることとも整合する）と割り当てたが、これは統合仕様書に明記されていない自分の判断である。

### 4.2 統合仕様書を読んで新たに見つけた未確定事項

矛盾解消ドキュメントのA〜H（8項目）以外で、本計画作成のために統合仕様書を読み直す過程で見つけたもの。

1. **§25の箇条書きに出現しない横断機能の帰属Phaseが未定義**（通知・ヘルプ・アクセシビリティ・ステータス/サポート・教材複製・共同編集）。§2.3・§3の該当行で個別に判断を記載したが、統合仕様書自身はこれらをどのPhaseに属させるか一度も明言していない。実装計画を書く段階で、各Phaseの完了条件に横断機能の分担を追記するかどうかの判断が必要。
2. **§18.3の利用枠制限軸（同時授業・市場数、AIクレジット）とPhase順序の関係が明示されていない**。§25はF（組織・契約）をE（AI強化）の後に置いているが、その理由（利用枠の一部軸がC・Eの存在を前提とする）は明文化されていない。本計画の §1.2・§1.4 で自分の解釈として補ったが、実装着手前に確認しておくとよい。
3. **§17.3「一般公開権限を学校側で制限可能」がFの基本組織設定で足りるのか、Hのポリシー継承機構（§20.3）まで必要なのかが未定義**。GがFのみに依存するか、Hの一部機能を先出しする必要があるかは、Gの実装計画作成時に確定させる必要がある。

## 6. Feature Flag と一括公開の方針

§25末尾「Feature Flagで未完成機能を非表示にし、一括公開前に内部テストを行う」を具体化する。

### 6.1 Phaseの成果物とフラグの対応

| Phase | 隠すべき成果物 | 想定フラグ名（例） | 備考 |
| --- | --- | --- | --- |
| A | なし（内部基盤のみ。ユーザーに見える画面を持たない） | — | 旧市場・旧APIの廃止方針（§25 Phase A）は既存利用者がいない前提（§1）なので、切替用フラグより「旧コード削除」で足りる |
| B | 新しい授業UI全体（教師画面・生徒画面・教室表示） | `lessonPlatformV2` | 既存利用者がいないため、フラグの目的は移行ではなく内部テスト中の非公開 |
| C | 社会科の常時売買市場 | `subjectSocialStudies` | 需給・ノイズ・価格ガードの既定値（§4.1）が未確定な間は特に隠す価値が高い |
| D | 家庭科シミュレーション | `subjectHomeEconomics` | CとDは独立して公開判断できる（1.3の並行関係と対応） |
| E | Guided Lesson Builder／AI Lesson Studio | `guidedLessonBuilder` / `aiLessonStudio` | §15.2「AIを使わない経路」があるため、AI部分だけ個別に止められる粒度が必要。§15.4の組織単位AI無効化と統合的に設計する |
| F | 学校組織・課金・上位組織 | `orgBilling` | §18.8の支払方法のうちカード決済は決済事業者選定（§5）が前提。請求書・手動状態は決済事業者なしで先に有効化できる |
| G | マーケットプレイス | `marketplace` | §15.4に学校単位のマーケットプレイス無効化があるため、グローバルフラグと組織別トグルの両方が要る |
| H | エンタープライズ管理画面 | `enterpriseAdminConsole` | §20.1の役割別メニュー非表示の仕組みと重なる部分がある |

### 6.2 公開前に確認すること

一括公開の前に、次を満たしていることを確認する。

- 該当Phaseの §27 受け入れテスト項目がすべてグリーン（2.1の対応表を使う）
- 該当Phaseの §31 チェックリスト項目がすべて完了（2.2の対応表を使う）
- §30-5「セキュリティルールはEmulatorで生徒、教師、管理者、別組織、停止済みメンバーを検証する」が実施済み
- §22.2の法務・学校規程確認が完了している（実データを扱うB以降が対象）
- §5の外部依存（Blaze/Cloud Tasks、決済事業者）が公開対象機能に必要な範囲で準備済み
- 内部テスト（実装者自身、可能なら第三者による試運転）で§27の該当分類を一通り実施している
