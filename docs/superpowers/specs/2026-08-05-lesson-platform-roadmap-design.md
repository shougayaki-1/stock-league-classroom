## 背景

現在のStock League Classroomは、チーム参加、売買、価格変動、ランキング表示、結果出力までを備えたリアルタイム株式市場シミュレーターのMVPとして動作している。一方で、授業教材として見ると次が不足している。

- 社会科（公共・政治経済）: 「価格がなぜ動いたのか」を生徒が検証できない。ニュースの影響が全銘柄一律で産業ごとの波及を表現できず、生徒の売買量が価格に影響しないため需要と供給による価格形成を扱えない。
- 家庭科（家庭基礎・家庭総合）: 株式の短時間売買しか扱えず、生活設計の中での資産形成を扱えない。

同時に、複数校での利用を見据えると、組織単位の権限・データ統制・ライセンスの仕組みが存在しない。

本ドキュメントは、これらを解決するための全体ロードマップと、実装前に確定しておくべき基盤設計を定義する。個別フェーズの詳細設計は別スペックとする。

## 基盤設計

以下のうち、所有モデルの統一・招待方式・開発順序・約定処理の移行時期は利用者の意思決定による確定事項である。それ以外は技術的な帰結であり、実装時の検証対象とする。

### 1. 所有モデルを組織所有に統一し、1ユーザーは複数組織へ所属できる

全リソースを `orgId` 所有とする。個人利用者にはアカウント作成時に「個人組織」を自動生成し、メンバー1名の組織として扱う。

| | 個人向け | エンタープライズ向け |
| --- | --- | --- |
| 組織 | 自動生成、メンバー1名 | 管理者が作成、メンバーN名 |
| 招待 | 不可 | 可（招待リンクまたはコード） |
| 管理者ページ | 非表示 | 表示 |
| 所有モデル | 同一 | 同一 |

理由: 個人はuid所有・組織はorgId所有という二経路にすると、セキュリティルールとUIが二重管理になる。所有経路を1本にすることで分岐が消える。

**1ユーザーは複数組織へ所属できる。** 教師は個人組織に加えて、勤務校、兼務校、研究会組織などへ同時に所属し得る。単一の所属を前提にしてはならない。

教材を組織間で動かす操作は4種類を区別し、所有権が変わるかどうかを利用者に明示する。

| 操作 | 所有権 | 用途 |
| --- | --- | --- |
| 複製 | 複製先の組織へ移る（元も残る） | 個人教材を学校で使えるようにする |
| 移動 | 移動先の組織へ移る（元は消える） | 教材を学校の資産にする |
| 共有 | 元の組織のまま | 所有権を渡さずに他組織へ利用を許可する |
| 派生 | 派生先の組織へ移り、元との関係を記録する | 他校の教材を自校向けに改変する |

学校組織へ移動した教材は、作成者の異動・退職後も学校側に残る。暗黙に移管せず、所有権が変わることを操作時に明示する。

データ構造:

```
users/{uid}
  personalOrgId
organizations/{orgId}
  type: personal | school | association
  ownerUid
organizations/{orgId}/members/{uid}
  role
  status
  joinedAt
templates/{templateId}
  orgId
  createdByUid
  currentVersionId
```

**個人組織はクライアントから作らせない。** 多重ログインや通信の再試行によって、同一ユーザーに複数の個人組織が作られる可能性がある。決定的なIDを用い、冪等な Callable Function またはAuth起点のサーバー処理で作成する。

```
organizations/personal_{uid}
```

処理内容:

```
既に個人組織がある  → 既存の orgId を返す
存在しない          → 組織、owner メンバーシップ、orgAccess を作成して orgId を返す
```

`users/{uid}.personalOrgId` はトランザクションで一度だけ設定する。

### 2. 権限は3層で管理する

カスタムクレームだけで組織権限を管理してはならない。理由は3つある。

1. 1ユーザーが複数組織へ所属するため、単一の `orgId` クレームでは表現できない。
2. プランはユーザーではなく組織の属性である。同じ教師が個人組織では無料プラン、学校組織では有料プランということが起こり得る。
3. カスタムクレームは合計1,000バイトの上限があり、所属組織すべてを格納する用途には適さない。

| 層 | 保持する情報 | 用途 |
| --- | --- | --- |
| カスタムクレーム | `operator` などサービス全体の権限のみ | 運営者操作。頻繁に変わらないものに限定する |
| Firestore `organizations/{orgId}/members/{uid}` | `role`、`status` | 組織権限の正本 |
| RTDB `orgAccess/{orgId}/{uid}` | `role`、`status`、`revokedAt` | 授業中に必要な権限のミラー |
| Cloud Functions | プラン、利用枠 | 課金・約定・公開・管理操作の最終判定 |

RTDBのルールは他データベースを参照できないが、同一RTDB内であれば `root.child(...)` で別パスを参照できる。授業中に必要な権限をRTDBへミラーすることで、この制約を解消する。

Firestoreルール内の `get()` は追加の読み取りとして課金されるが、組織権限を参照するのはテンプレート操作や結果操作といった低頻度の経路に限られる。授業中の高頻度な経路はすべてRTDB側であり、そちらはミラーを参照する。

教師の資格判定（`email_verified`、`sign_in_provider`）は標準のトークンフィールドで行えるため、独自クレームを追加しない。

#### 失効の仕組み

Firebase の `revokeRefreshTokens` は新しいIDトークンの取得を止めるが、発行済みのIDトークンは有効期限（通常1時間）まで使用され得る。即時遮断には、失効時刻をデータベースへ保存してセキュリティルールで照合する必要がある。

```
orgAccess/{orgId}/{uid}
  role
  status                 // active | suspended
  membershipVersion
  revokedAtSeconds
```

ルールの判定条件は次の形になる。

```
status == 'active' && auth.token.auth_time >= revokedAtSeconds
```

**単位に注意する。** Firebase の `auth_time` は秒、JavaScript の `Date.now()` はミリ秒である。`revokedAtSeconds` は秒で統一する。

メンバー削除は次の順序で行う。いきなりドキュメントを削除すると、監査と再試行ができなくなる。

1. Firestore のメンバーシップを `suspended` にする
2. RTDB の `orgAccess` を `suspended` にする
3. `revokedAtSeconds` を更新する
4. `revokeRefreshTokens` を実行する
5. 必要な非同期処理の完了後にメンバーシップを削除する

#### ミラーの整合性

`orgAccess` は Firestore メンバーシップの複製であるため、同期失敗が起こり得る。次を保証する。

- Firestore を正本とする
- RTDB の `orgAccess` へは Admin SDK のみが書き込める
- `membershipVersion` を持ち、古いバージョンの書き込みを無視する
- 同じイベントを再実行しても結果が変わらない（冪等）
- 不整合を検出した場合はアクセスを拒否する側へ倒す
- 管理画面から再同期できる
- 定期的に整合性を検査する

**「Firestore更新成功、RTDB更新失敗」の状態で、削除済みメンバーがRTDBへアクセスし続けないことが最も重要である。** そのため、メンバーの追加・停止・削除は通常のクライアント書き込みではなく、単一の Callable Function に集約する。

### 3. 価格の公開範囲をフェーズごとに変える

生徒端末が将来の価格を計算できる情報を受け取れば、開発者ツールからも計算できる。区間を短くしても、売買が可能である限り無リスクの取引が成立する。したがって**売買が可能な時間帯に将来価格の情報を配信してはならない。**

| フェーズ | 生徒へ公開する情報 | クライアント側の計算 | 書き込み |
| --- | --- | --- | --- |
| 売買フェーズ（ラウンドモード） | 現在価格と締切時刻のみ | なし | なし |
| 変動・公開フェーズ（ラウンドモード） | フェーズ情報一式（開始価格、確定した終了価格、開始/終了時刻、シード） | あり（滑らかな描画） | フェーズ開始時に1回 |
| クラシックモード | 現在価格のみ | なし | 従来どおりホストが書き込む |

売買締切後の公開フェーズでは、価格は既に確定しており取引もできないため、終了価格が読めても不利益がない。ここでフェーズ情報を配信することで、毎秒の書き込みなしに滑らかな価格アニメーションを実現できる。

生徒へ公開する売買フェーズ中のデータ構造:

```ts
interface PublicRoundQuote {
  roundId: string
  currentPrice: number
  tradingClosesAt: number
}
```

`targetPrice`、`endPrice`、`seed` は含めない。

**脆弱性の解消は型から行う。** セキュリティルールを変えるだけでは、今後のコード修正で誤って `runtime` を公開側へ戻す事故が起こり得る。現在ひとつのオブジェクトになっている `LivePrice` を、型レベルで分離する。

```ts
interface PublicLivePrice {
  price: number
  updatedAtMillis: number
}

interface PrivatePriceRuntime {
  mode: 'PHASE'
  phaseId: string
  startPrice: number
  endPrice: number
  startAtMillis: number
  endAtMillis: number
  seed: number
}
```

RTDBのパスも分ける。公開側は既存の `prices` を維持し、runtime のみを移す。

```
liveMarkets/{marketId}/prices/{stockId}                 // 生徒が読める
liveMarkets/{marketId}/privatePriceRuntime/{stockId}    // ホストのみ
```

セキュリティルールのテストで次を確認する。

| 対象 | `prices/{stockId}/price` | `privatePriceRuntime` | 市場ルート全体 |
| --- | --- | --- | --- |
| 生徒 | 読める | 読めない | 読めない |
| 教師（ホスト） | 読める | 読める | 読める |

クラシックモードのサーバー化（サーバーが数秒ごとに現在価格を公開する方式）は採用しない。Cloud Schedulerの最短実行間隔は1分であり、それより短い周期にはCloud Runの常駐かCloud Tasksの自己連鎖が必要になる。これは「常駐インスタンスを使用しない」というコスト方針と衝突する。クラシックモードは当面ホストのブラウザが価格を書き込む現行方式を維持し、ノード分離のみを行う。

**時刻の扱い:** `.info/serverTimeOffset` はネットワーク遅延の影響を受けるため、画面表示の補正には使えるが、約定時刻や価格の権威にはできない。約定は必ずサーバー時刻で処理する。

#### 2つのモードの位置づけ

両モードの制約は異なる。ドキュメント上も画面上も名称で区別する。

| | ラウンドモード | クラシックモード（連続） |
| --- | --- | --- |
| 位置づけ | 新しい授業向けの標準方式 | 既存互換方式 |
| 価格の権威 | サーバー（Cloud Functions） | 教師のブラウザ |
| 約定 | 締切時に一括 | 注文ごとに即時 |
| 毎秒の価格書き込み | なし | あり（当面維持） |
| 教師のタブが背面・スリープ | 影響を受けない | **価格更新と約定が停止する** |
| 先読み脆弱性 | 原理的に発生しない | ノード分離により解消 |
| 需給の価格反映 | 可能 | 不可 |

**「市場進行方式の刷新により教師のタブが背面でも動く」という効果は、ラウンドモードにのみ当てはまる。** クラシックモードのホスト依存は当面残る。コスト試算も2モードを分けて行う。

### 4. 約定はモードごとに分ける

ラウンドモードとクラシックモードで約定関数を分離する。ひとつの関数で分岐すると条件が増え、検証が難しくなる。

**ラウンドモード: `settleRound()`（一括約定）**

```
売買フェーズ中
  チームが注文案を保存・変更（確定前は何度でも変更可）
  ↓ 締切
settleRound を1回実行
  1. ラウンド状態を確認する
  2. 冪等キー（settlementId）で二重実行を防ぐ
  3. 全チームの確定注文を読み込む
  4. ニュースの銘柄別影響を計算する
  5. 需給（注文量の偏り）を価格へ反映する
  6. 全チームを同一条件で約定する
  7. 結果を保存する
  8. ラウンドを SETTLED にする
```

一括約定を採用する理由は2つある。

1. **需給連動価格を実装できる。** 締切まで総需要が確定しないため、注文量を価格へ反映するには一括処理が必須である。これは社会科で「需要と供給による価格形成」を扱うための中核機能であり、教師がテンプレート側のフラグでオン・オフを切り替える。入門授業ではオフにしてシナリオ駆動のみとする。
2. **生徒が判断を修正できる。** 締切まで注文案を変更できることで、「決定」と「執行」が分離され、チームでの議論の時間が確保される。

#### 約定価格の決定

**Phase 1では、全注文を売買フェーズ中に公開されていた価格で約定する。注文の純需要は、ニュース等のイベント影響とともに次ラウンドの開始価格へ反映する。**

```
売買フェーズの表示価格: 500円
  ↓ 全チームの注文を500円で約定
  ↓ 買い越しを次ラウンドへ反映
次ラウンドの開始価格: 520円
```

この方式を選ぶ理由:

- 生徒は画面で見た価格で取引できる。「500円で買ったのに520円だった」という不満が生じない
- 残高不足の判定が単純になる
- 「自分たちが買ったから次に上がった」という因果が説明しやすい
- 処理に循環が生じない

**需給反映後の価格で約定する方式は採用しない。** 価格が上がると買える数量が減り、数量が減ると需給が変わるため、注文数量と価格決定が相互依存して循環する。板寄せ方式（買いと売りの注文を突き合わせる）は、数量不一致、一部約定、注文の優先順位、成行と指値の区別、清算価格の決定まで必要になるためPhase 1には重すぎる。いずれも将来の発展機能とする。

#### 価格変化の合成式

ニュース影響と需給影響を両方実装するため、合成方法を確定する。**変化率を加算してから上下限で丸める**方式を採用する。乗算方式との数値差はわずかだが、加算方式は授業で分解して説明できる。

```ts
rawChangePercent = newsImpactPercent + demandImpactPercent + otherImpactPercent
appliedChangePercent = clamp(rawChangePercent, -20, 20)
nextPrice = currentPrice * (1 + appliedChangePercent / 100)
```

上下限の ±20 は既存の `NEWS_IMPACT_LIMIT`（`src/lib/market/hostTrading.ts:225`）を引き継ぐ。

結果公開時には内訳を分解して表示する。これが振り返り画面の中心的な表示になる。

```
ニュースの影響   -10%
生徒の需要       + 4%
最終変化率       - 6%
```

需給影響の式は金額ベースとする。株数ベースでは高価格銘柄と低価格銘柄を比較できない。

```ts
netDemandValue = totalBuyValue - totalSellValue
demandRatio = netDemandValue / stockMarketSize
demandImpactPercent = clamp(demandRatio * sensitivity, -maxDemandImpact, maxDemandImpact)
```

**`stockMarketSize`（銘柄ごとの市場規模）はテンプレートに存在しない概念であり、追加が必要である。** 現在の `TemplateCompany`（`src/lib/templates/types.ts`）は名前・シンボル・初期価格・価格フェーズのみを持ち、発行株数や時価総額に相当する値がない。

教師に発行株数を設定させるのは負担が大きいため、相対的な重みで表現する。

```ts
stockMarketSize = 全チームの初期資金合計 × marketSizeWeight   // marketSizeWeight の既定値は 1.0
```

全チームが全資金を1銘柄へ投じたとき `demandRatio` が概ね 1.0 になる。教師は数値を意識せず「この会社は小さい」と設定するだけで変動しやすさを調整でき、元の構想にあった「発行株式数が少ない企業ほど動きやすい」という学習内容を扱える。

#### チーム注文の編集と競合処理

チーム共有口座では、同じチームの複数の生徒が同時に注文案を操作する。単純な上書き（Last Write Wins）では、他の生徒の入力を消してしまう。

`revision` による楽観的並行制御を用いる。

```ts
interface TeamRoundDecision {
  revision: number
  orders: PlannedOrder[]
  reason: string
  referencedDocumentIds: string[]
  updatedByParticipantId: string
  updatedAt: number
  submitted: boolean
  submittedAt?: number
}
```

```
読み込んだ revision: 7、更新要求の revision: 7 → revision 8 として保存
読み込んだ revision: 7、サーバーは既に revision 8 → 競合として再読み込みを促す
```

授業上の運用ルール:

- チーム全員が注文案を編集できる
- 誰かが「チームの回答として確定」を押す
- 確定後も締切までは再編集できる
- 教師が締め切った時点の最新版を採用する

「トレーダー役だけが確定できる」という制約は、役割分担機能を実装した後の任意設定とする。

この構造は、現在の参加者ごとの `orders/{participantId}/pending`（`src/lib/market/liveMarketTypes.ts`）とは異なる。ラウンドモードではチーム単位の注文案を正本とし、現行の参加者ごと保留注文はクラシックモード専用として残す。

**クラシックモード: `placeContinuousOrder()`（即時約定）**

```
注文受信
  ↓
サーバー時刻の正規価格を算出
  ↓
残高と保有を確認
  ↓
即時約定
```

**実装上の注意:** FirestoreおよびRTDBのイベントトリガーは少なくとも1回の配信であり、順序も保証されない。約定と課金に関わる処理はデータベーストリガーに任せず、Callable関数またはHTTP関数と冪等キーで実装する。

**コスト:** いずれもイベント駆動であり、常駐インスタンスを使用しない。ラウンドモードでは1授業あたり数回から十数回の呼び出しに収まる。

### 5. `orgId` をPhase 1で導入し、その時点からルールで強制する

全ドキュメントに `orgId` と `createdByUid` を持たせる。Phase 1の時点では組織のUIを実装しないが、**セキュリティルールによる強制は最初から行う。**

クライアントが自由に `orgId` を設定できる状態では、誤った、あるいは不正な `orgId` を持つドキュメントが作られる。組織ルールを有効にする段階でデータを信用できなくなる。Phase 1の時点から次を保証する。

- `orgId` は作成時に、そのユーザーの正しい個人組織IDでなければならない
- `orgId` は通常の更新で変更できない
- `createdByUid` は `request.auth.uid` でなければならない
- `createdByUid` は変更できない
- 組織間の移動は専用のCloud Functionのみが実行できる

対象とするドキュメント:

- テンプレートとそのバージョン
- 市場（Firestoreの `markets` と RTDBの `liveMarkets/{marketId}/meta` の両方）
- 授業結果
- AI設計セッション
- アップロードされた資料
- マーケットプレイス掲載情報

対象外:

- `officialTemplates`（運営者が管理する）
- `serviceStatus`（グローバル設定）
- `templateShares`（capability方式の共有リンク。組織メンバーシップとは無関係）
- `marketJoinCodes`（capability方式の参加コード）
- 生徒の匿名認証プロファイル

### 6. テンプレートのバージョン管理をPhase 1で導入する

**下書きと版を分ける。** 編集のたびに版を作ると大量のバージョンが発生する。編集中は下書きへ自動保存し、教師が明示的に「版を保存」したときのみ不変の版を作る。

```
templates/{templateId}
  orgId
  createdByUid
  draft                          // 編集中の内容。自動保存
  currentPublishedVersionId
  status
templates/{templateId}/versions/{versionId}
  schemaVersion
  content                        // 作成後は変更不可
  createdByUid
  createdAt
  changeSummary
  parentVersionId
```

| 操作 | 動作 |
| --- | --- |
| 通常の編集 | `draft` へ自動保存 |
| 「版を保存」 | 不変の版を作成する |
| 市場作成 | 必ず版を固定する |
| AIの提案中 | 一時的な提案として保存する（`draft` は書き換えない） |
| AIの提案を採用 | `draft` へ反映する |
| マーケットプレイス公開 | 公開する版を指定する |

市場には `templateId`、`templateVersionId`、`templateSnapshot` を持たせる。

現在も市場作成時に `templateSnapshot` を保存しており、実施中の授業がテンプレート編集の影響を受けない仕組みは既にある。バージョン管理はそれに加えて、AI編集前後の差分確認、共同編集での巻き戻し、派生元の記録、翌年度の再利用を可能にする。

スキーマv2を定義するPhase 1で同時に導入する。後から追加すると、テンプレートの保存構造を二度書き換えることになる。

| Phase | 内容 | 依存 |

| 0 | 現行版の安全化 | — |
| 1 | 授業エンジンv2（スキーマ、バージョン、ラウンド、一括約定、需給、組織の器） | 0 |
| 2 | 授業運用（Research Desk、コントロールルーム、Guided Lesson Builder、試運転） | 1 |

AIを課金基盤より前に置くのは、教師がAIとの対話に何を求めるかを早期に検証するためである。限定ユーザーへの提供と課金なしの運用であれば、ライセンス基盤に依存しない。

**個人単位のデータ削除・エクスポートは Phase 1〜2 で無料機能として提供する。** 未成年の学習・行動データ（氏名、予想、判断理由、取引履歴）を扱うため、学校の情報管理規程、契約、プライバシーポリシーへ対応する上で優先度の高い基盤機能である。この機能をエンタープライズ限定にしたり後段のフェーズへ回したりしない。Phase 7 で扱うのは組織単位の統制（保持ポリシー、一括削除、監査ログ）に限る。

具体的にどこまでが法令上の必須要件かは、サービス提供主体、学校との契約関係、公立・私立の別、学校設置者の規程、保存するデータの範囲、利用目的、保護者同意の扱いによって変わる。正式提供の前に確認する。

### Phase 0: 現行版の安全化と基準値計測

Phase 1へ進む前に、現存する脆弱性を塞ぎ、削減効果を評価するための基準値を得る。

完了条件:

- 生徒アカウントで `endPrice` と `seed` を取得できないこと
- Rules Emulator のテストで先読み経路を検証済みであること（生徒・教師それぞれの読み取り可否）
- 50分・80人相当の負荷試験を実施済みであること

- 書き込み回数とデータサイズを記録済みであること

### Phase 1: 授業エンジンv2

依存関係のある6段階で構成する。

**1.1 組織の器**

- アカウント初回ログイン時に個人組織を自動生成する
- 全ドキュメントへ `orgId` と `createdByUid` を追加し、基盤設計5の強制ルールを実装する
- 組織のUIは実装しない

**1.2 LessonTemplate v2 スキーマとバージョン管理**

`schemaVersion` を持つ新形式を定義し、v1（現行 `TemplateSpec`）からの変換関数と、基盤設計6のバージョン構造を実装する。データ構造のみを対象とし、UIは変更しない。

v2で追加する主な要素:

- `meta`: 教科、学年、想定時間、難易度
- `objectives`: 主目標・副目標・問い
- `classroom`: 推奨人数、チーム規模、端末環境、個人予想の有無
- `market`: 価格モード（ラウンド／連続）、需給連動の有無、資産定義
- `rounds`: ラウンドとフェーズの構成
- `events`: ニュースと銘柄別の影響（`assetId` ごとの方向と大きさ、遅延ラウンド数）
- `documents`: 企業プロフィール、統計、決算などの資料
- `assessment`: 評価指標、振り返りの問い
- `teacherGuide`: 進行メモ、解説、よくある誤解

既存の3つの公式テンプレート（学園祭・宇宙都市・地域再生）はv2へ変換する。

**1.3 Cloud Functions基盤と価格の秘匿**

- Blazeプランへ移行し、予算アラートを設定する
- `functions/` パッケージを新設する
- `src/lib/pricing/pricingCore.ts` をクライアントとFunctionsが共有できる形へ切り出す
- クライアントは `.info/serverTimeOffset` を購読し、補正した時刻で表示価格を算出する

**1.4 ラウンド進行と一括約定**

- ラウンドとフェーズ（導入／情報収集／個人予想／チーム相談／売買／変動／解説／振り返り）の状態遷移を実装する
- 教師の「次へ」操作で進行する（タイマー自動進行は標準にしない）
- 売買フェーズ中はチームの注文案を保存・変更できるようにする
- `settleRound()` を実装する（冪等キー、需給反映を含む）
- `placeContinuousOrder()` を実装する

**1.5 銘柄別ニュースと需給連動**

- `applyNewsImpact`（`src/lib/market/hostTrading.ts:232`）を銘柄別影響に対応させる
- 遅延影響（次のラウンドで効く、数ラウンド後から下落する）を実装する
- 注文量の偏りを価格へ反映する需給連動を実装し、テンプレート側のフラグで切り替える
- 出来高を表示する

**1.6 予想・判断理由の記録と振り返り**

- 売買前に個人予想を入力させる。標準は方向（上昇／横ばい／下落）、確信度、根拠の3点とし、変化率の予想は発展設定とする
- 注文に判断理由と参照したニュースを紐づける
- チーム内で予想を比較する画面を用意する（記名／匿名を教師が選択）
- ニュースと株価を重ねた時系列グラフを表示する
- 個人単位の結果削除とCSVエクスポートを提供する

チーム共有口座は維持する。個人予想は「個人の思考の記録」であり、口座を分割するものではない。

**評価指標の扱い:** 自動計算できるものと、教師が判断すべきものを分ける。

| 自動計算 | 教師の評価（ルーブリック） |
| --- | --- |
| 予想方向の正解率 | 根拠の論理性 |
| 参照した資料の数 | 反対方向の影響も考慮したか |
| 複数の情報源を比較したか | 短期と長期を区別したか |
| 判断を変更した回数 | 社会全体への影響を考えたか |
| 予想と実際の行動が一致しているか | |
| 資産推移、分散度、目標達成 | |

「根拠の妥当性」をシステムが自動採点することはしない。政治・経済分野では唯一の正解がない場合があり、自動採点は教育上不適切である。AIによる補助コメントは可能だが、正式な成績判定の権威にはしない。

### Phase 2: 授業運用の質

- **Research Desk（生徒）**: 授業フェーズに応じて必要な画面だけを表示する。企業ページ、ニュース一覧、統計資料、チームノート、注文画面をフェーズごとに出し分ける
- **コントロールルーム（教師）**: 設定項目の羅列ではなく「次に押すボタン」を中心にする。進行台本、教師用メモ、残り時間、参加状況を表示する
- **試運転モード**: 授業前に固定戦略のダミーチームで通し実行し、時間配分と価格変動を確認する

**Guided Lesson Builder（教師向けの選択式授業設計）**

教師が選択肢に答えるだけで授業案が出る機能を、AIより前にルールベースで実装する。生成AIが利用できない学校やAPI障害時にも動作する。

選択項目:

- 科目
- 主な学習目標
- 授業時間
- 生徒数
- 端末環境
- 個人／チーム活動
- 資料読解の深さ
- 授業テーマ
- 難易度

出力は「簡単な案」「標準案」「発展案」の3案とする。1案に決め打ちせず、教師が比較できるようにする。

内部では次の中間表現を生成する。

```ts
interface LessonIntent {
  subject: 'SOCIAL_STUDIES' | 'HOME_ECONOMICS'
  primaryObjective: string
  secondaryObjectives: string[]
  durationMinutes: number
  studentCount: number
  deviceMode: 'ONE_PER_STUDENT' | 'ONE_PER_TEAM'
  activities: string[]
  researchDepth: 'NEWS_ONLY' | 'COMPANY_INFO' | 'FINANCIALS'
  difficulty: 'INTRODUCTORY' | 'STANDARD' | 'ADVANCED'
  theme?: string
}
```

`LessonIntent` はPhase 3のAI Lesson Studioも入力として受け取る。これにより、ルールベースのおすすめ、AIとの対話設計、手動の詳細設定が同じデータモデルを共有する。

### Phase 3: AI Lesson Studio ベータ

限定ユーザーへ提供し、課金は行わない。教師がAIとの対話に何を求めるかを検証することが目的である。

**「課金なし」と「無制限」は別である。** ライセンス基盤がない段階でも、次の制限を実装してからベータを公開する。

- 利用者は運営者が許可したアカウントに限定する
- 1日および1か月あたりのハード上限をFunctions側に設ける
- 1回の最大入力サイズを制限する
- アップロード資料の最大ページ数と容量を制限する
- 高価なモデルの利用は禁止または運営者限定とする
- `serviceStatus/global.aiGenerationEnabled` による緊急停止を用意する
- 利用量と原価をログへ記録する

実装方針:

- AI APIはブラウザから直接呼ばず、Cloud Functionsを経由する。APIキーはFunctions側のみに置く
- `LessonIntent` を受け取ってテンプレート案を生成する
- 画面は左にAIとの対話、右に授業プレビューを置く。AIの文章を読まないと設定状況が分からない構造にしない
- AIは一度に多数の質問を出さず、一問ずつ進める
- AIは構造化JSONを生成し、JSON Schema検証と試運転を通してから教師が承認する。AIがデータベースへ直接書き込む経路は設けない
- 変更前・変更後・変更理由を提示し、教師が採用／修正／却下を選ぶ
- 生徒の氏名、メールアドレス、生徒ID、個別成績、市場の参加コードはAIへ送信しない
- 生成物であることを画面に表示する
- 価格計算、ラウンドの状態遷移、注文処理、評価計算はAIに実行させず、通常のプログラムで処理する

AIが生成したテンプレートに対する機械的な検証項目:

- 授業時間内に収まるか
- 価格が0以下にならないか
- 特定銘柄だけが必ず勝つ構造になっていないか
- 生徒が判断する前に答えが表示されていないか
- ニュースと価格変動が矛盾していないか
- 振り返り時間が確保されているか
- 実在企業の事実を架空情報として混ぜていないか
- 不適切な金融勧誘表現がないか
- 個人情報が含まれていないか

### Phase 4: 家庭科モード

株式売買とは異なるデータモデルを必要とするため、独立したサブプロジェクトとして別スペックを作成する。

対象となる要素:

- 資産クラス（普通預金、定期預金、債券、国内株式、海外株式、投資信託、現金）
- 架空の生活プロフィール（年齢、収入、貯蓄、将来の目標）
- 収入・支出・積立（1ラウンド＝1年または5年）
- ライフイベント（進学、就職、結婚、出産、住宅購入、病気、失業、災害、物価上昇、金利上昇）
- 目標達成型の評価（生活目標の達成、緊急予備資金、分散度、最大下落耐性、手数料）

**保険は資産クラスと分けてモデル化する。** 保険は保有価値や収益率を持つ資産ではなく、保険料を支払い特定の事故や病気の際に給付を受けるリスク移転の商品である。資産配分の円グラフに株式と同列で並べるのは教育上も誤りである。

```ts
assets: Asset[]
insurance: InsuranceContract[]
cashFlows: CashFlow[]
```

**比較条件を揃える。** 標準の授業では、全チームに同じ人物プロフィール、同じ初期資産、同じ収入、同じイベントを適用する。そうしないと、投資判断の違いではなく人物条件の違いで結果が変わり、比較にならない。異なる人物プロフィールを割り当てるのは発展授業とする。

### Phase 5: 組織・ライセンス・決済

- 組織、メンバー、招待の実装（招待リンクまたはコードによる参加）
- ロールの定義: `owner`（組織作成者・課金責任）、`admin`（メンバー管理・データ統制・教材承認）、`teacher`（通常メンバー）
- 基盤設計2の3層権限モデルの実装（Firestoreメンバーシップ、RTDBミラー、Functionsでの最終判定）
- メンバー削除時の `revokedAt` 記録とトークン失効
- 教材の複製・移動・共有・派生
- 市場作成をFunctions経由へ集約し、プラン別の上限を判定する
- AI利用枠の本運用
- 決済の導入

**市場作成をFunctionsへ移す際、現行の冪等性を維持する。** `creationStatus` と `recoverMarketCreation` による部分失敗からの復旧は、FirestoreとRTDBを跨ぐ処理として必要な仕組みである。加えて、利用枠だけ消費して市場作成に失敗する事態を避けるため、「仮確保 → 作成 → 成功時に確定 → 失敗時に返却」の順序で処理する。

**定員の扱いを変更する。** 現在は `capacity == 80` という固定値だが、サービス上限と授業ごとの想定人数を分離する。

```ts
maxParticipants: 80        // 全プラン共通のサービス上限
expectedParticipants: 35   // 教師が設定する想定人数
```

`expectedParticipants` はチーム編成と進行時間の提案に使う。最大定員はプランで変えない。プランで変えるのは同時に開催できる市場数とする。

### Phase 6: テンプレートマーケットプレイス

- 組織を越えた公開、検索、複製
- 公開区分（公式／認証済み／コミュニティ／限定公開／非公開）
- 派生関係の記録（バージョン管理はPhase 1で導入済み）
- 通報と審査

既存のURL共有（`templateShares`、capability方式）は用途が異なるため維持する。

**2種類の管理者を区別する。** Phase 6では、サービス運営者向けの最低限の審査画面が必要である。学校組織向けの管理画面はPhase 7でよい。

| サービス運営者（`operator`） | 学校組織（`admin`） |
| --- | --- |
| 通報の確認 | 学校メンバーの管理 |
| 教材の非公開化 | 学校教材の管理 |
| 公式認証の付与 | 生徒データの保持 |
| 投稿者の利用停止 | 組織ライセンス |
| 審査履歴 | |

**審査基準は政治的中立性だけでは足りない。** 少なくとも次を含める。

- 個人情報の混入
- 著作権と出典
- 実在企業についての虚偽や誤認を招く記述
- 金融商品の推奨と誤解される表現
- 差別的・不適切な内容
- 教科の学習目標との対応
- 政策・政治的論点における複数視点の提示
- AI生成物の確認状況
- 技術的に最後まで実行可能か
- 所要時間が現実的か

すべてを公開前に人手で審査すると運用が成立しないため、公開区分ごとに審査の重さを変える。

| 区分 | 審査 |
| --- | --- |
| コミュニティ公開 | 自動検査＋事後の通報対応 |
| 認証済み | 人手審査 |
| 公式 | 運営側が作成、または厳格審査 |

### Phase 7: エンタープライズ管理者機能

**メンバーとライセンスの管理**

- 招待リンクの発行と失効
- メンバー一覧、ロール変更、削除（`revokedAt` の記録とトークン失効を伴う）
- 割り当て済み／残ライセンス数の表示

**生徒データの組織単位の統制**

- 保持期間の組織ポリシー設定
- 組織全体の一括削除とエクスポート
- 監査ログ
- 管理者向けの検索
- 年度単位のアーカイブ

個人単位の削除・エクスポート・匿名化はPhase 1〜2で全利用者へ提供済みであり、ここで扱うのは組織単位の統制に限る。

**組織内の教材共有と承認**

- 組織テンプレートライブラリ
- 下書き → 承認 → 公開 のステータス管理
- 承認権限は `admin` ロールが持つ

**利用状況のダッシュボード**

- 教員別の授業実施回数
- AI利用枠の消費状況
- 同時開催市場のピーク

### 課金ポイントの根拠

1. **AI利用枠**: コストがAPI呼び出しへ直結するため、従量制または月次上限として設計しやすい
2. **同時市場数**: 複数教室を同時開催する需要と一致する
3. **共同編集と組織内共有**: 教科主任が教材を作り他の教員が調整する運用に対応する。学校単位ライセンスの中心的価値
4. **長期保存と組織統制**: 年度を越えた教材・結果の管理は学校の運用要求と一致する

購買形態は学校・自治体単位の年間ライセンスを想定する。個人課金はAI利用枠を中心とする。

## コスト方針

前提: Blazeプランへ移行する。

| 項目 | 方針 |
| --- | --- |
| RTDB | ラウンドモードでは価格更新がラウンド境界とイベント公開時に限定される |
| Firestore | Research Deskの資料閲覧が読み取りを増やす。組織権限の `get()` は低頻度経路に限定する |
| Cloud Functions | イベント駆動のみとし、常駐インスタンスを使用しない |
| AI | 教員の教材作成時のみ。生徒操作と授業中は呼び出さない |

**削減効果の記述について:** 現在、価格更新に伴うRTDBトランザクションは50分授業で約3,000回発生する。これは市場ルートへのトランザクションであり、その1回の中で全銘柄を更新する。ラウンドモードでは価格更新がラウンド境界とイベント公開時に限定されるため、**価格更新トランザクション数**は99%以上削減できる見込みである。ただし、RTDBの課金対象となる転送量には参加状態、予想、注文、ポートフォリオ、およびプロトコルのオーバーヘッドも含まれるため、**総転送量の削減率は事前に断定できない。Phase 0で基準値を計測し、Phase 1完了後に実測で比較する。**

**予算アラートは自動停止しない。** Google Cloudの予算アラートは通知のみであり、設定額に達しても利用は継続する。費用の反映にも遅延がある。したがってアプリケーション側にも停止機構を持たせる。既存の `serviceStatus/global` を拡張する。

```
serviceStatus/global
  acceptingNewMarkets
  aiGenerationEnabled
  fileUploadEnabled
  marketplacePublishingEnabled
  maxActiveMarkets
```

組織ごとの利用量を集計する。

```
usage/{orgId}/{yyyyMM}
  marketRuns
  aiCredits
  uploadedBytes
  concurrentMarketPeak
```

## 中核となる処理の流れ

```
LessonTemplate v2
  ↓
不変のテンプレートバージョン
  ↓
授業（Lesson Run）の作成
  ↓
ラウンド開始
  ↓
資料の公開
  ↓
個人予想
  ↓
チーム相談
  ↓
チーム注文案の確定
  ↓
settleRound を1回実行
  ↓
ニュースの銘柄別影響 ＋ 需給影響を計算
  ↓
全チームを一括約定
  ↓
価格と解説を公開（この時点でフェーズ情報を配信し、クライアントが描画）
  ↓
振り返り
```

## 検証の方針

各フェーズの完了時に、実際の授業で使用してフィードバックを得てから次へ進む。全フェーズを実装してから初めて実運用に出す進め方は取らない。

Phase 1完了時点で、社会科のラウンド制授業が実施可能な状態になることを目標とする。
