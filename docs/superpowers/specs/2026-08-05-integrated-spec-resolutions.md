## A. 3秒バッチの実行機構

### 問題

統合仕様書 §26-11 は「教師のブラウザ停止で市場処理が止まる設計にしない」を不変条件とし、§12.9 は処理間隔3秒（変更範囲1〜10秒）を既定とする。しかし**何がその3秒を刻むのか**が定義されていない。Cloud Scheduler の最短実行間隔は1分であり、この用途には使えない。

### 決定

**Cloud Tasks の自己連鎖を用いる。**

```
区間 N の締切
  → Function が起動（Cloud Tasks からのディスパッチ）
  → 注文検証・約定・次価格計算
  → nextBatchAt を DB へ書き込む
  → 区間 N+1 のタスクを scheduleTime = now + interval で予約
```

Firebase Functions のタスクキュー機能（`onTaskDispatched` 系）を用い、Firebase のデプロイ体系に収める。**具体的なAPI名とバージョンは実装着手時に context7 で最新ドキュメントを確認すること。**

### 選定理由

| 観点 | Cloud Tasks 自己連鎖 | Cloud Run 長時間リクエスト |
| --- | --- | --- |
| 待機中のコスト | ゼロ | ゼロ（最小インスタンスを置かない場合） |
| 同時開催市場 | 独立した連鎖として並行。追加コストは線形 | 市場数だけインスタンスが必要 |
| 実行時間の上限 | なし | 60分。長い授業では再接続が必要 |
| デプロイ体系 | Firebase に収まる | 別サービスの運用が増える |
| 時刻精度 | 揺らぎあり | 高い |

統合仕様書 §18.3 が「同時授業・市場数」をプラン制限軸に置いているため、同時開催時の振る舞いを重視した。月200授業・1授業あたり約400区間で8万タスク程度であり、Cloud Tasks の無料枠内に収まる見込み。

### 実装上の必須事項

1. **カウントダウンは `nextBatchAt` で駆動する。** Cloud Tasks の実行時刻には揺らぎがあるため、クライアントで3秒を数えてはならない。サーバーが書いた `nextBatchAt` までの残り時間を表示し、超過したら「処理中」と表示する。
2. **`batchId` を冪等キーとする。** Cloud Tasks は重複実行しうる。同一 `batchId` の処理は1回だけ成立させる（統合仕様書 §12.13、§26-4）。
3. **連鎖の切断を検知する。** タスクが失われると市場が停止したまま無音になる。`nextBatchAt` を過ぎても次の区間が処理されない場合に検知し、教師へ通知して再開できる仕組みを持つ。
4. **市場停止・再開との整合。** 停止時は連鎖を止め、再開時に新しい連鎖を開始する。停止中に残ったタスクが発火しても、市場状態を見て何もせず終了すること。

## B. 資金拘束の基準時点

### 問題

統合仕様書 §12.16 は注文送信時に「参考価格×株数」を拘束し、利用可能現金から差し引くとする。一方 §12.15 は「合計が**区間開始時の**利用可能現金を超えた場合」に全不成立とする。拘束が進行する中で区間開始時の値を基準にすると、拘束済みの金額を二重に数える。

### 決定

**§12.15 の「区間開始時の」を削除し、2段階の判定に統一する。**

| 時点 | 基準 | 性質 | 失敗時 |
| --- | --- | --- | --- |
| 注文送信時 | 参考価格 × 数量 | ソフト。利用可能現金の表示から差し引く | 注文を受け付けない（UIで防ぐ） |
| 区間締切時 | 約定価格 × 数量 | ハード。実際の約定価格で再判定 | その区間の買い注文をすべて不成立 |

`利用可能現金 = 現金 − 拘束中の買い注文額（参考価格ベース）` とし、注文追加のたびに減少する。締切時は約定価格で総額を再計算し、現金を超えていればその区間の買い注文を全不成立とする（一部約定はしない。統合仕様書 §26-14）。

§12.16 自身が「約定価格上昇で資金不足なら、区間の買い注文は不成立」と書いており、この2段階を意図していると解釈できる。

### 売却側

同じ構造とする。注文送信時に売却注文中の株数を売却可能数から差し引き、締切時に保有株数で再判定する。売却合計が保有株を超えていればその区間の当該売り注文を全不成立とする。

## C. 需給計算に使う数量

### 問題

統合仕様書 §12.14 は同一区間・同一銘柄の買いと売りを差し引く（買い5株＋売り2株＝買い3株）。§12.10 は「買い・売りの合計は次価格の需給影響へ使う」とのみ記し、これが相殺前（総額）か相殺後（正味）か決まらない。値動きの大きさが変わる。

### 決定

**需給影響には相殺後（正味）を使う。出来高の表示には相殺前（総額）を使う。**

```ts
// 需給影響 — 実際に約定した正味の数量から算出する
netDemandValue = Σ(正味買い金額) − Σ(正味売り金額)

// 出来高表示 — 相殺前の総取引量
displayedVolume = Σ(買い数量) + Σ(売り数量)
```

### 理由

§12.14 により実際に約定するのは相殺後の数量である。総額で需給を計算すると、成立していない取引が価格を動かすことになる。

またゲーム性の問題がある。総額方式では「100株買い・98株売り」を同一区間に出すことで、正味2株分の資金しか使わずに100株分の買い圧力を発生させられる。生徒が気づけば市場を操作できてしまう。

一方、出来高は現実の市場でも総取引量を指す。価格圧力は需給の偏りから生じ、出来高は活動量を示す別の指標である。両者を分けることで経済的にも正確になり、統合仕様書 §12.5 の「出来高相当の売買量」を情報カテゴリとして提示する意味も保たれる。

## D. 乱数シードの導出規則

### 問題

統合仕様書 §7.4 は `LessonRun` に単一の `randomSeed` を持たせ、§12.22 は3秒区間ごとに市場ノイズを適用し、§7.7 と §27.2 はリプレイでの再現を要求する。しかし区間ごとのシードをどう導出するかが定義されていない。

### 決定

**単一の `randomSeed` から決定的に導出する。**

```
社会科の市場ノイズ:
  seed = derive(`${randomSeed}:${restoreGeneration}:${stockId}:${batchIndex}`)

家庭科のイベント:
  seed = derive(`${randomSeed}:${restoreGeneration}:${roundIndex}:${eventKey}`)
```

`restoreGeneration` は E で導入する。

### 実装上の必須事項

1. **`Math.random()` を使わない。** 文字列ハッシュ（FNV-1a 等）と決定的な擬似乱数（mulberry32 等）を組み合わせ、外部依存なしで実装する。
2. **丸め処理と同じ単一モジュールへ固定し、クライアントとサーバーで共有する。** 既存の `src/lib/pricing/pricingCore.ts:41` の `createPhaseRuntime` は `seed = Math.random() * 1000` を既定引数に持っており、これを共有パッケージへ持ち込むと非決定性が混入する。新実装では同じ誤りを繰り返さない。
3. **同一入力に対して同一出力になることをテストで保証する。** リプレイの前提であり、統合仕様書 §27.2 の受け入れテスト項目でもある。

## E. チェックポイント復元と履歴の不変性

### 問題

統合仕様書 §26-2 は「約定済み注文を削除して履歴を書き換えない」を不変条件とする。一方 §12.17 は「重大障害のみ、市場全体をチェックポイントへ戻す」とする。復元は事実上、約定を取り消す操作である。

### 決定

**復元を「巻き戻し」ではなく「追記」として扱う。**

1. 復元操作そのものを `LessonEvent` として追記する（`type: 'CHECKPOINT_RESTORED'`、復元先の `checkpointId`、理由、実行者を含む）
2. 元の約定レコードは削除しない。復元後の状態計算から除外されるだけである
3. `LessonRun` に `restoreGeneration: number` を持たせ、復元のたびに加算する

### `restoreGeneration` が必要な理由

区間50のチェックポイントへ戻して続行すると、区間51以降が再び実行される。イベントログには区間51のイベントが2組存在することになる。`restoreGeneration` がないと、リプレイ時にどちらの系列を再現すべきか判別できない。

D のシード導出にも同じ理由で必要である。世代を含めないと、復元後の区間51が復元前と同一のノイズを生じ、「やり直しても同じ結果になる」という不自然な挙動になる。

### 結果の確定

`COMPLETED` 時点で有効な世代（最新の `restoreGeneration`）の系列のみを最終結果とする。過去の世代は監査とリプレイのために保持する。

## F. 予想チェックポイントの評価時点

### 問題

統合仕様書 §12.32 は「いつの予想を評価するかを明確にし、売買履歴だけから予想を推定しない」と要求するが、**評価時点そのものは定義していない**。常時売買のため、予想の直後から価格は動き続ける。

### 決定

**各予想チェックポイントが評価時点を明示的に持つ。**

```ts
interface PredictionCheckpoint {
  id: string
  triggeredByInformationId?: string   // 通常はニュース・決算の公開が契機
  evaluationTarget:
    | { type: 'AFTER_BATCHES'; count: number }        // N区間後の価格と比較
    | { type: 'NEXT_INFORMATION' }                    // 次の情報公開時点と比較
    | { type: 'MARKET_CLOSE' }                        // 市場終了時点と比較
}
```

既定は `{ type: 'AFTER_BATCHES', count: N }` とし、N は教材設定とする。50分授業では市場時間が20分程度のため、情報公開1回あたり数分に相当する区間数が目安になる。

### 市場を止めるかどうか

統合仕様書 §12.27 が既に「公開時に自動停止」「公開後の確認時間」を教師設定として持つ。予想チェックポイントはこれと組み合わせる。

- 止める設定: 確認時間中に予想を入力させ、再開後の価格で評価する
- 止めない設定: 予想入力と売買が並行する。入力の締切は最初の評価対象区間の開始までとする

止めない設定では、予想を出さずに売買だけ行う生徒が出る。統合仕様書 §12.33 の評価観点「予想精度」は未入力を減点ではなく対象外として扱い、教師画面に未入力者を表示する。

## G. 家庭科と `MARKET` フェーズの関係

### 問題

統合仕様書 §7.5 の `LessonPhase.type` には `'MARKET'` があり、§13 の家庭科は3秒バッチの市場を持たない。家庭科が `MARKET` を使うのか不明。

### 決定

**家庭科は `MARKET` フェーズを使わない。** 資産配分や購入の判断は `DECISION` フェーズで行う。

理由は時間の単位が異なることである。社会科の市場は3秒区間で価格が動く実時間シミュレーションだが、家庭科は1ラウンドが5年（既定）であり、資産の収益は年次収益率で計算する（§13.15）。同じフェーズ型を共有すると、進行エンジンに教科ごとの分岐が入り込む。

`LessonRun.subject` が `'HOME_ECONOMICS'` のとき、`MARKET` フェーズを含む教材は開始前チェック（§8.3）でエラーとする。

## H. `REFLECTION` 状態と市場停止の関係

### 問題

統合仕様書 §8.2 の `REFLECTION` は「売買・主要判断を停止」、§12.25 の市場停止は「新規注文を拒否」であり、機能が重なる。両者の関係が未定義。

### 決定

**層が異なるものとして扱う。**

| | 層 | 誰が行うか | 元へ戻せるか |
| --- | --- | --- | --- |
| 市場停止（§12.25） | 市場の操作 | 教師。`RUNNING` 中に何度でも | 戻せる（§12.26 の再開） |
| `REFLECTION`（§8.2） | 授業実施の状態 | 教師。授業を振り返りへ進める | 戻さない前提 |

`REFLECTION` へ遷移する際、その一部として市場停止を実行する。したがって「`REFLECTION` なのに市場が動いている」状態は存在しない。逆に「市場停止中だが `RUNNING`」は正常な状態である（ニュース公開時の確認時間など）。
